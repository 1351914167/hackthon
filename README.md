# 雾隐镇

一款以语音证据和可验证复盘为核心的中文语音狼人杀。玩家标记关键原声，赛后沿着发言、票型和查验重建推理链；系统负责主持和规则，灵汐 API 提供语音智能。该特色是后续迭代目标，当前演示尚未实现声证链。

当前仓库包含演示界面、灵汐 STT/TTS 本地代理，以及独立的确定性规则引擎、内存事件存储和私密快照投影。领域模块已通过测试，尚未接入现有演示服务器和前端；多人联机与完整语音房仍未交付。

规则 review 已完成。当前按照 [新版开发计划](DEVELOPMENT_PLAN.md) 建立 PR/CI 基线，Hackathon 交付完整可演示体验，最终交付可维护的工程级项目。后续新功能通过 PR 和 CI 迭代；本轮基础 PR 不增加业务功能。设计和验收资料见：

本地启动（Node.js 24）：

```bash
node server.js
```

默认访问地址：`http://127.0.0.1:4173`

```bash
LINGXI_API_KEY='your-key' node server.js
```

密钥只应配置在服务端环境变量中，不应写入前端代码、提交到仓库或记录在日志中。

## 产品分析

### 产品机会

线下狼人杀的张力来自语气、停顿、抢话和沉默。现有线上体验的主要问题不是角色数量不足，而是组局、语音秩序和复盘证据没有形成可信闭环。

| 问题 | 典型表现 | 产品机会 |
| --- | --- | --- |
| 组局成本高 | 缺人、忘词、规则争议导致流局 | 标准板子一键开局，系统自动主持和结算 |
| 语音秩序弱 | 多人抢麦、主持人持续控场 | 阶段级发言权、顺序麦、自由麦和可见倒计时 |
| 私密信息风险 | 客户端提前收到不应看见的角色或结果 | 服务端按玩家裁剪快照，客户端永远拿不到多余信息 |
| 复盘价值丢失 | 关键发言、查验和票型无法还原 | 结构化时间线、转写摘要和胜负转折复盘 |
| 断线破坏牌局 | 玩家掉线后整局等待或直接结束 | 重连宽限、临时托管和身份快照恢复 |

### 目标用户

1. **熟人开黑组**：希望一分钟内完成建房和邀请，不需要人工讲解流程。
2. **进阶逻辑玩家**：关注发言顺序、票型、查验链和可验证的对局证据。
3. **轻社交玩家**：需要低压力破冰、清晰的发言边界和较低的规则学习成本。

首版聚焦 18–35 岁中文语音社交玩家，仅支持固定 9 人板子，目标局长为 25–40 分钟。12 人局和 AI 补位属于远期方向。

### 一句话定位

给想立刻开一局的朋友们，一间能听懂、会控场、可复盘的语音狼人杀房。

## 产品设计

### 设计原则

- **先保证公平，再增加智能**：胜负、技能和投票由确定性规则引擎决定，模型不能修改结算结果。
- **语音状态必须可见**：玩家始终知道谁能说话、是否录音、是否传输、是否转写成功。
- **秘密只在需要时出现**：角色、队友和查验结果由服务端按玩家身份裁剪。
- **失败不破坏牌局**：语音服务异常时降级为文字事件和手动操作，规则状态继续可恢复。
- **复盘服务于下一局**：只保留能解释胜负的关键行动、票型和发言摘要。

### 核心体验闭环

```text
一分钟组局 -> 系统发身份 -> 夜间技能 -> 白天语音发言 -> 放逐公投
                              ^                         |
                              | 胜负未确定              | 胜负已确定
                              +------ 胜负判定 ----------+-> 证据复盘 -> 再来一局
```

### 首发规则：9 人标准局

| 阵营 | 角色 | 数量 | 能力 |
| --- | --- | ---: | --- |
| 好人 | 预言家 | 1 | 每晚查验一名玩家的阵营 |
| 好人 | 女巫 | 1 | 拥有一瓶解药和一瓶毒药，每瓶整局限用一次 |
| 好人 | 猎人 | 1 | 正常死亡时可开枪带走一名玩家 |
| 好人 | 平民 | 3 | 通过发言和投票找出狼人 |
| 狼人 | 狼人 | 3 | 每晚共同选择一名玩家袭击 |

好人放逐全部狼人获胜；狼人数量达到或超过其余存活玩家时获胜。首版不加入第三方阵营，避免新手学习成本和结算边界快速膨胀。

### 信息架构

```text
房间大厅                 席位确认                 牌局圆桌              案件复盘
创建 / 加入 / 选择板子 -> 麦克风 / 准备 / 领取身份 -> 发言 / 技能 / 投票 -> 阵营 / 票型 / 关键转折
   ^                                                                          |
   +------------------------------- 再来一局 --------------------------------+
```

### 牌局主界面

主界面按“场上状态、当前行动、个人秘密”分为三个稳定区域：

- **圆桌席位**：展示存活、离线、出局、当前发言者和自己的位置。
- **中央舞台**：展示阶段、倒计时、当前发言者、实时转写和控麦入口。
- **个人情报**：展示自己的角色、技能结果、推理便签和结构化时间线。

移动端将席位压缩为顶部横向列表，中央舞台保持主操作区，个人情报移动到牌局内容下方，避免文字与主要按钮重叠。

### 语音交互

1. 服务端根据阶段、座位和存活状态授予发言权。
2. 客户端明确展示录音、上传、转写和失败状态。
3. 玩家结束发言后，录音经雾隐镇网关发送至灵汐 `gpt-4o-transcribe`。
4. 转写结果绑定玩家、局号、阶段和时间点，再广播给有权查看的客户端。
5. 系统主持音由灵汐 `gpt-4o-mini-tts` 生成，并明确标注为 AI 合成语音。
6. 原始音频默认不落盘；复盘只保存结构化事件和经用户同意保留的转写文本。

### 关键异常状态

| 异常 | 用户反馈 | 系统行为 |
| --- | --- | --- |
| 麦克风权限被拒绝 | 提示开启权限或改用文字操作 | 不开始录音，不阻塞阶段推进 |
| 灵汐转写超时 | 展示“转写失败，可重新发言” | 丢弃临时录音，保留阶段与计时状态 |
| 主持音合成失败 | 显示同内容文字提示 | 规则状态正常推进 |
| 玩家短暂断线 | 座位显示重连倒计时 | 保存本人可见快照，宽限期内不释放座位 |
| 玩家长期离线 | 提示离线与超时状态 | 按冻结规则跳过行动或弃权；AI 托管另行确认 |
| 房主离线 | 自动迁移主持权限 | 规则状态机不依赖房主客户端 |

### 指标设计

北极星指标：**有效完局数 / 周**。

首版有效完局需满足：9 名真人开局、完成胜负结算、没有因语音链路中断而终止。该指标用于后续联机版本，当前原型不产生有效完局统计。

辅助指标：

- 建房到开局的中位耗时。
- 首局完成率和七日内再次组局率。
- 灵汐转写首字延迟、成功率和重试率。
- 每局抢麦冲突次数与主持人手动干预次数。
- 断线恢复成功率。
- 复盘页分享率和“再来一局”转化率。

## 项目架构

### 总体架构

```text
+------------------------+     HTTP + SSE（规划）  +-----------------------------+
| 响应式 Web 客户端      | <---------------------> | 雾隐镇服务端                |
|                        |                         |                             |
| - 牌局界面             |                         | - 房间服务（待实现）        |
| - 麦克风与音频播放     |                         | - 权限与玩家快照裁剪        |
| - 当前玩家可见状态     |                         | - 独立规则引擎              |
+------------------------+                         | - 内存事件存储              |
                                                   | - 灵汐语音网关              |
                                                   +--------------+--------------+
                                                                  |
                                                        灵汐专用 API 调用
                                                                  |
                                                   +--------------v--------------+
                                                   | 灵汐 API                    |
                                                   |                             |
                                                   | - gpt-4o-transcribe         |
                                                   | - gpt-4o-mini-tts           |
                                                   | - Realtime（待验证/实现）    |

```

此图是接入目标：目前只有静态页面和 STT/TTS 代理在 `server.js` 中运行，`src` 领域模块尚未接线。首版规划采用 HTTP 提交动作、带 Bearer 的 `fetch` 流式读取 SSE；生产级 WSS 需要另行确认依赖。

### 架构边界

#### 客户端

- 采集麦克风音频并播放主持音。
- 渲染服务端下发的当前玩家可见快照。
- 提交技能、投票、准备和发言等用户意图。
- 不自行判定胜负，不持有完整角色表，不持有灵汐长期密钥。

#### 房间与规则状态机

- 房间服务管理加入、准备、当前房主与重连；在 `/start` 内原子校验当前房主与 9 人全准备，再创建 Game 并立即开局。
- 规则引擎负责阶段、行动顺序和胜负；应用层注入时间与发牌结果，服务端调度器负责到期检查。
- 接收玩家意图并验证身份、阶段、存活状态和技能次数。
- 以确定性事件推进牌局，支持重放、恢复和复盘。
- 模型输出只能生成表达内容，不能改变规则状态。

#### 权限与快照裁剪

- 为每名玩家生成不同的状态视图。
- 隐藏其他玩家身份、狼人夜间选择和未公开技能结果。
- 观战者只接收公开信息，出局玩家的额外权限由房间规则决定。
- 白名单覆盖死亡、票型、查验和技能库存的嵌套字段，不整块复制内部对象。
- 客户端只持有自己的可见内容 `version`，不接收权威事件序号；SSE 使用按查看者隔离的 cursor。

#### 灵汐语音网关

以下是待完成的接入要求；现有本地代理尚未实现鉴权、限流、并发和上游超时等完整保护。

- 封装 Authorization，避免密钥暴露到浏览器。
- 固定允许的模型、接口和参数范围。
- 负责请求大小限制、超时、限流、审计和错误标准化。
- 不在日志中写入 Authorization 或原始语音正文。
- 所有语音智能能力严格使用灵汐 API，不接入 LiveKit、Agora 等第二语音供应商。

### 牌局状态机

```text
固定席位启动 -> 发放身份 -> 夜间行动 -> 黎明结算
                                      |
                          狼杀猎人时先完成开枪
                                      |
                      白天发言 -> 公投 -> 放逐遗言
                                            |
                                放逐猎人时先完成开枪
                                            |
                         胜负判定：结束 或 下一轮夜间
```

状态转换必须由服务端执行。客户端重复提交、越阶段提交或来自已出局玩家的无效行动应被拒绝，同时保持幂等。

### 核心数据模型

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `Room` | `id`、`status`、`ruleset`、`phase`、`round` | 房间与当前阶段 |
| `Seat` | `seatId`、`playerId`、`alive`、`connectionState` | 玩家席位与连接状态 |
| `SecretRole` | `seatId`、`role`、`team` | 服务端保存，按本人/狼队友/结束态权限投影 |
| `Action` | `id`、`phase`、`actorSeatId`、`type`、`targetSeatId` | 技能、投票等玩家意图 |
| `GameEvent` | `seq`、`type`、`payload` | 仅服务端使用，公开范围由投影层白名单决定 |
| `VoiceSegment` | `seatId`、`phase`、`status`、`transcriptConsent` | 语音处理元数据，不默认保存原始音频 |

```text

   |               |                  |                |               |
   |-- 授予发言权 ->|                  |                |               |
   |               |-- 上传临时音频 ->|                |               |
   |               |                  |-- 转写请求 ---->|               |
   |               |                  |<- 转写结果 -----|               |
   |<- 玩家、阶段、时间点与转写 -------|                |               |
   |-- 验证并写入事件 ------------------------------------------------>|

```

### 安全与隐私

- 灵汐密钥只存在于服务端环境变量。
- 所有玩家行动必须绑定短期座位令牌，并在服务端验证权限。
- 私密角色和夜间结果通过视图裁剪隔离，不依赖前端隐藏。
- 原始音频默认只用于即时处理，处理结束后释放。
- 转写全文的留存和复盘展示需要明确同意，并提供房间级关闭选项。
- 日志记录请求 ID、耗时、状态码和模型，不记录密钥或完整音频内容。
- 对转写、合成和 Realtime 分别设置并发、时长和费用上限。

```text
     |

     |

                                                   +-> 写入结构化牌局事件
```

语音失败不能改变或丢失规则状态。房间状态以服务端事件序列恢复，语音结果是附属事件而不是结算依据。

## 当前限制

- 当前牌局数据为前端演示状态，尚未接入多人房间和持久化存储。
- STT/TTS 代理需要有效的 `LINGXI_API_KEY`，目前未进行真实供应商调用验收。
- 本地代理仍缺少生产鉴权、并发限制、超时和错误脱敏；接入真实计费密钥后的保护需要在语音阶段完成。
- Realtime 上游协议与 WSS 代理尚未验证；原声已规划分段与自管实时媒体两个交付阶段，具体 E2 实现与依赖需在对应 PR 验证，不能把转写广播视为九人原声语音房。
- 内存事件存储不会在进程重启后恢复牌局；后续网络重连不等于进程恢复。
- 现有 `product.html` 保留原型设计，当前范围与接入边界以本 README、规则规范和协议文档为准。
- AI 托管不在首版范围；治理、观战权限和费用控制按新版计划逐步补齐。
